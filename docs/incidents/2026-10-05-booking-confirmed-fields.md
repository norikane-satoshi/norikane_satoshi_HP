## 原因

`choice-panel-state.ts` の `feature-length-under-60m` は工程見積もりのために
`projectLengthMinutes: 60` に変換する。従来の `buildBookingConfirmationItems`
は相談要約から表示値を取り、`jobContext` のカテゴリと数値を「長編」「1時間」
へ整形した。範囲回答が確定した尺へ変わり、カテゴリ選択肢の広い意味も失われた。

最終媒体・お任せ・相談したいは、初期選択や無回答時の既定値ではなく実際の
回答だった。ChoicePanel の新規選択は空から始まる。今回の記録から、これらを
ボットが創作したとは結論できない。

加えて回答フラグは `jobContext` の存在からも立つため、フラグだけでは回答証拠
にならない。Widget の旧補足生成も `jobContext` を予約メモへ流していた。
最終確認の案件条件は読み取り専用で、相談者が直接修正できなかった。

## 修正の契約

- 予約の条件は user message の一致する選択回答・明示した値から作る。
  見積もり用数値・assistant message・回答フラグを値の根拠にしない。
- 選択肢の原文、範囲、概数を保持する。根拠がない項目は「未確認」。
- 最終確認で条件を編集でき、編集後は同意を取り直す。旧保存カードの表示値は
  回答証拠のバージョンがないため初期値に使わない。
- サーバーが同じ確認済み条件でメモを構成する。BookingGroup、通知メール、
  Calendar の description / Notion 同期元へ同じ値を渡す。
- 条件が未確認・修正された場合、古い工程見積もりによる作業日の自動追加をせず、
  相談者が選んだ日程だけを依頼する。

実予約の送信・既存予約の更新・顧客への再通知は今回の修正には含めない。
